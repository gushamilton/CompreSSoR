# CompreSSoR benchmark record

This directory contains the compact benchmark write-up and the small,
committed result tables that support the package README. Large source GWAS
files, temporary stores, Slurm logs, and reference data remain on BluePebble
and are not copied into GitHub.

## Headline Pareto benchmark

The README figure is generated by:

```bash
Rscript scripts/plot-final-factors.R
```

The script uses `ggplot2` and `ggrepel`. It plots all 34 measured keyed
formats from the final FinnGen chr1 screen, draws the Pareto path, and labels
only the frontier plus the TSV.gz baseline. The exact benchmark contract is
recorded in:

- `inst/benchmarks/final-factors-20260804/final-summary-updated.csv`;
- `inst/benchmarks/final-factors-20260804/final-frontier-updated.csv`;
- `inst/benchmarks/final-factors-20260804/final-selected-runs.csv`;
- `inst/benchmarks/final-keyed-20260804/final-keyed-registry.csv`.

The comparison is same-data and key-bearing: every candidate stores a
self-contained position plus directed REF→ALT identity. The canonical
reference is not charged to any individual GWAS store. The locked default is
the native Pcodec implementation because it gives the best compression-first
trade-off among the validated options.

## Storage and read-speed scaling

The scaling benchmark was run on BluePebble compute nodes against a public
Pan-UKB per-phenotype summary-statistics file. The official source describes
these files as GRCh37 `.tsv.bgz` files with approximately 29 million variants
and AF, beta, SE, and p-value fields; see the
[Pan-UKB per-phenotype documentation](https://pan.ukbb.broadinstitute.org/docs/per-phenotype-files/index.html).

For this benchmark we selected the first 21 million valid autosomal biallelic
SNP rows with usable EUR AF, beta, SE, and p-value values. The source remains
GRCh37; this is a storage/access scaling benchmark, not a liftover or
harmonisation validation. Coordinates were restricted to the GRCh38 primary
chromosome lengths solely to keep the CompreSSoR identity key collision-free.

The formats are deliberately limited to the three useful comparison points:

| Format | Stored benchmark payload |
|---|---|
| TSV.gz | `chrom`, `pos`, `REF`, `ALT`, `beta`, `SE`, `EAF`, `p` |
| Parquet q9 | position/substitution plus q9 Z, arcsine EAF8, log2(SE)8; Zstd level 9 |
| CompreSSoR Pcodec | self-contained identity key plus Pcodec Z, EAF, and SE streams; beta/p derived on read |

At each row count, each format was written once and read three complete times.
The result table records write time, median/min/max full-file read time,
storage bytes, and the checksum. The compression ratio is

```text
TSV.gz bytes / candidate bytes
```

so a value above 1 means that the candidate is smaller than TSV.gz. No
external reference is included in any candidate size. The results are:

- `data/panukb-scaling-fine-10k-1m.csv`: 10k–100k in 10k steps, then 100k–1m in 100k steps;
- `data/panukb-scaling-1-10m.csv`: 1m–10m in 1m steps;
- `data/panukb-scaling-11-21m.csv`: the completed large-row-count chunk;
- `data/panukb-scaling-summary.csv`: the merged table used for the full curve.

The plotting helper is `scripts/plot-panukb-scaling-1-10m.R`; it produces
three ggplot panels for absolute storage, compression ratio, and median
whole-file read time. The small-row-count plot uses a log x-axis so the 10k
through 1m behaviour is visible.

### Reproduction on BluePebble

The benchmark source preparation and Slurm launchers are:

```bash
sbatch scripts/download-panukb-scaling.sbatch
sbatch scripts/prepare-panukb-scaling.sbatch
sbatch scripts/benchmark-panukb-scaling-array.sbatch
sbatch scripts/benchmark-panukb-scaling-fine.sbatch
```

These jobs use the `test` partition and compute nodes; the login node is used
only for submission, status checks, and small file transfers. Each job writes
only its result CSV plus temporary per-size stores and removes those stores
after each measurement.

## Other benchmark records

The remaining files under `inst/benchmarks/` are retained as historical or
scope-specific evidence: native reader tests, BP threading checks, VCF/Tabix
comparisons, MR access experiments, and older format screens. They should not
be mixed into the headline Pareto plot unless their input, identity contract,
cache state, and access workload match the final keyed protocol.
